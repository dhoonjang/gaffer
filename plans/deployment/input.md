LLM API 비용은 무료 인프라와 분리한다.
- 사용자마다 독립적인 게임 세계를 갖는다. 사용자끼리 같은 세계를 공유하는 멀티플레이 요구는 없다.
- 모델의 서사와 결정적 게임 원장의 경계, Zod 검증, 기존 시뮬레이터와 도메인 경계를 보존한다. 모델 ID는 `config/llm.yml`이 소유한다.
- 세이브 마이그레이션은 금지되어 있다. `SAVE_VERSION` 불일치, 배포 중 실행 중인 턴, 클라이언트·서버 시뮬레이터 버전 일치를 반드시 다룬다.
- 기존 사용자 `.data`와 `.log`를 변경하지 않는다. 비밀값을 읽거나 문서에 싣지 않는다. 로컬 전체 테스트·e2e·유료 LLM 호출은 실행하지 않는다.
- 서비스 공급자 기능·제약·요금은 공식 자료로 확인하고 링크를 남긴다. 추정 비용과 실측 비용을 구별한다.
- 각자 먼저 독립 설계한다. Claude는 독립안 작성 완료 전 Codex 설계 파일을 읽지 않는다. 이후 서로의 가정과 장애 경로를 검토한다.
- 비용을 비교할 때 무료 제공량·초과 과금·휴면 정책·카드 등록 필요·DB 백업·네트워크·로그·운영 부담을 포함한다. 10명 이하 초대 베타와 이후 확장을 구분한다. 초기 상주 replica, 유료 PITR, 고가 플랜은 기본값으로 두지 않는다. 무료 범위를 넘는 전환 조건과 데이터 손실 허용 범위를 수치로 밝힌다.

## 설계가 답해야 할 질문

1. 현재 배포를 막는 구체적인 코드 경계는 무엇인가?
2. 프론트엔드, API, 턴 실행, 경기 검증, 비동기 기억 편집을 어디서 실행할 것인가?
3. 인증·초대·소유권·운영자 권한·다른 기기와 탭의 동시 접근을 어떻게 처리할 것인가?
4. 큰 세이브의 저장·원자성·중복 요청·장애 복구·삭제·백업을 어떻게 보장할 것인가?
5. 끊긴 스트림과 서버 재시작 이후 같은 작업을 어떻게 찾아 이어받을 것인가?
6. 10명 이하 접속을 실제 턴/초, LLM 요청/초·토큰/분, CPU, 메모리, DB 연결, 트래픽으로 어떻게 환산하며, 이후 300명까지 어디를 확장하는가?
7. 비용 상한·제공자 쿼터·재시도 폭증·한 사용자 독점을 어떻게 막을 것인가?
8. 피드백, 제품 분석, 오류, 호출 원문, 감사 기록을 어떻게 연결하고 구분할 것인가?
9. 개인정보와 게임 원문의 보관·접근·삭제 범위는 무엇인가?
10. 배포·롤백·호환성·장애 대응·출시 검증·단계별 구현 순서는 무엇인가?
11. 권장 조합 하나와 대안의 선택 조건, 남은 제품 의사결정은 무엇인가?

## 산출물

- 각 독립안: 근거, 아키텍처, 주요 데이터 계약, 실패 경로, 부하·비용 가정, 실행 순서와 출시 게이트.
- 교차 검토: 중요도, 발견 사항, 해당 근거, 채택·기각 이유, 남은 불확실성.
- 최종안: 결정된 권장 설계가 한 문서에서 읽혀야 한다. 검토 기록은 별도 문서로 둔다.

## 후속 대화의 프레임워크·실행기 질문

- “Next JS 단일 구성이 괜찮은 거 맞아? 프레임워크를 백엔드, 프론트엔드 구분할 필요 없어?”
- “꼭 next js 를 써야하는 이유가 있어? 그냥 react랑 nest 조합 같이 써도 되지 않나?”
- “별도 작업실행기는 왜 필요한거야? 전체 인프라 구조를 다시 정리해서 설명해줘”

후속 설명은 React/Vite + NestJS를 기준으로 한다. Next를 필수로 전제하지 않는다. 작업 실행 역할과 별도 서비스 배포의 필요성을 구분하고, 초기 10명 규모에서의 비용·복잡성·복구 이점을 설명한다. 코드 이전이나 실제 배포를 실행한 것으로 해석하지 않는다.
