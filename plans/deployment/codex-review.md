# Claude 독립안에 대한 Codex 검토

검토일 2026-10-16. 대상은 [Claude 독립안](claude-design.md)의 최초 단일 VM 안과 실제 코드다. 최신 요구는 [공통 입력](input.md)의 **초기 동시 접속 10명 이하·초대제·무료 인프라 우선**이다. 아래는 구현 결함 보고가 아니라 제안의 채택 여부를 판단한 기록이다.

| 중요도 | 검토 사항                                                    | 근거와 판단                                                                                                           | 최종 처리                                                                                   |
| ------ | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 높음   | 유료 서울 VM·리전 디스크는 최신 조건과 다름                  | 독립안 §0/8은 20~300명과 월 약 $160 이상 인프라를 기준으로 함                                                         | 초기에는 Cloud Run min 0·무료 DB/객체 저장소. VM 안은 파일 저장을 유지할 유료 대안으로 보존 |
| 높음   | 파일 rename과 SQL transaction은 한 원자 commit이 아님        | 독립안 §5.6의 transaction 안 rename은 파일 시스템 효과를 SQL rollback으로 되돌리지 못함                               | R2 불변 객체 선업로드 후 DB 참조·revision·receipt를 원자 commit. 실패 객체 GC는 별도        |
| 높음   | 호스트 장애 RPO 0의 근거가 부족                              | 현 persistence는 writeFileSync/renameSync를 사용하고 fsync 경계가 없음. rename의 원자성과 전원 장애 durability는 다름 | 프로세스 장애와 저장소 전체 손실을 구별하고, 무료안 DB 손실 RPO 24시간을 명시               |
| 높음   | 요청 ID 64개 보관은 장기 receipt 계약이 아님                 | §5.3~5.4. 오래된 재전송·입력 payload 변경·크래시 후 관측 원장 재조정에 한계                                           | 영구 operation receipt + input hash + revision CAS를 DB에 둠. 같은 key/다른 입력은 거절     |
| 높음   | 경기 client 임대에는 commit 시 epoch 검사가 필요             | §4.5의 client ID/만료만으로 takeover 전에 시작한 오래된 요청을 차단할 계약이 불충분                                   | 서버 epoch를 제출과 최종 commit에 검사. takeover는 기존 경기 작업의 실행권도 무효화         |
| 높음   | p90 비용 예약만으로 지출 상한을 보장 못함                    | §8.3. 평균 이상 호출·SDK 내부 retry·usage 없는 timeout이 누적 가능                                                    | 실제 외부 요청마다 permit·예약, unknown 상태를 보수적으로 남김                              |
| 중간   | 공개 전에 SAVE_VERSION을 올릴 필요는 선택한 저장 방식에 달림 | §5.3의 revision/request IDs는 게임 규칙 데이터가 아니라 운영 metadata로 분리 가능                                     | DB envelope에 보관. GameState의 모양·의미가 실제 바뀔 때만 SAVE_VERSION 판단                |
| 중간   | 서버 권위가 있다고 sim build 혼용이 해결되지는 않음          | §11.3의 reload는 저장된 진행 경기의 runtime 의미까지 변환하지 못함                                                    | 경기와 cohort의 runtime pin, 구 클라이언트 자산 보존                                        |
| 중간   | 역사적 개발 로그를 처리 성능으로 확정하면 안 됨              | 표본은 개발자 1명·여러 게임 버전·148개 LLM 턴. CPU는 M2 Max의 CLI                                                     | 크기/병목의 근거로 채택, cloud 부하·현행 모델 soak는 출시 게이트로 유지                     |

채택한 강점은 실제 저장/CPU/heap/응답 크기 확인, trace 수집과 오류 상세 노출 분리, lorebook 무제한 재시도 차단, 게임별 hot cache의 위치, 사용자 단위 비용 제한, 운영 route 전체 소유권 검사, SAVE_VERSION별 실행기 유지다. 무료 구성이어도 이 정확성 경계는 유지한다.

최종안은 프롬프트·모델을 바꾸지 않는다. 무료 모델로 교체해 비용을 맞추는 방식은 채택하지 않는다. 외부 제공자 요금과 약관의 상세 수치는 최종 채택한 공급자의 공식 자료를 직접 확인한다. 독립안의 VM/SLA·법률 세부·미래 모델 가격을 현재 권장안의 보장으로 옮기지 않는다.

Claude의 최신 무료안 재평가와 최종안 비판은 [claude-review.md](claude-review.md)에, 양방향 반영 결과는 [최종 합성 기록](review-results.md)에 정리한다.
