## 0. 결론

**정확성 계약은 Codex 안이 더 엄밀하다.** 작업 멱등 키와 payload 해시, lease와 fencing을 붙인 CAS 커밋, 복원 뒤 삭제 재적용, 타인 id의 404가 그것이다. 이 계약들은 최종안에 그대로 들어가야 한다.

**그러나 토폴로지와 비용은 확정된 요구와 맞지 않는다.** 확정된 요구는 "초대제, 안정성을 지키는 최소 비용"이다.

- AWS Multi-AZ RDS, Fargate 3개 서비스의 2 AZ 상주, ALB·NAT·CloudFront/WAF, Cognito를 Codex 안 스스로 월 $500~1,200으로 잡는다.
- 이것은 초대 50명 베타의 LLM 비용(약 $480/월 [추정])보다 크다.
- 세이브 저장 경로·작업 큐·이벤트 로그·S3 스냅샷·RLS·outbox를 첫 초대 **전에** 모두 새로 짜야 한다. 원장 위험이 가장 큰 부분을 먼저 다시 쓰는 순서다.

**치명적인 누락이 둘 있다.**

1. **Gemini의 지출 기반 등급 제약이 없다.** 10분 지출 한도, 연결된 프로젝트의 Gemini API를 멈추는 월 상한, Tier 3까지 30일 대기, 2027-01-01 가격 두 배가 빠졌다. 그래서 300명 계획이 그대로는 실행되지 않는다.
2. **LLM 비용을 실제 가격표나 실측 토큰과 잇지 않았다.**

**최종안 권고**

| 단계  | 구성                                                                                                                                       |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1단계 | Claude 토폴로지(단일 쓰기 호스트, 파일 세이브, 리전 디스크) + Codex의 정확성 계약을 단일 호스트에 맞게 옮긴 것                             |
| 2단계 | 트리거가 서면 Codex의 DB 작업·임대·fencing 모델로 간다. 세이브 저장소는 S3가 아니라 코디네이터가 제안한 **Postgres 압축 청크**를 쓴다(§6). |

## 3. 발견 사항 (중요도순)

### K1 · 치명 — Gemini의 지출 기반 등급 제약이 빠졌다

**발견**

- Codex는 "provider/project/model별 RPM·TPM admission"만 말한다.
- Gemini Developer API의 실제 묶음은 다음 셋이다 [공식, rate-limits·billing].
  - 등급별 **10분 누적 지출 한도**: Tier 1 $10, Tier 2 $50, Tier 3 $200.
  - **월 상한**: Tier 1 $250, Tier 2 $2,000. 닿으면 "결제 계정에 연결된 모든 프로젝트를 일시 중지"한다. 이 문구는 Gemini API 범위로 읽는다. 인프라까지 멈춘다고 단정하지 않는다(코디네이터 지적 반영).
  - **승급 조건**: Tier 2는 $100 + 3일, Tier 3은 $1,000 + 30일.
- 모델별 RPM과 TPM은 공개되지 않는다.

**영향**

- 300명 동시라면 턴 2.8/s × 턴당 약 $0.019 [추정]이다. 10분에 약 $32, 시간당 약 $190다.
  - 이 값은 **사고 토큰이 빠진 하한**이다. 어댑터가 `thoughtsTokenCount`를 세지 않는다(`gemini-adapter.ts:217`, §8.6).
- Tier 2의 월 상한은 약 10시간이면 닿는다.
- 2027-01-01부터 Flash 가격이 두 배라 10분 지출이 약 $62가 된다. Tier 3 없이는 불가능하다.
- Codex의 단계 계획(10 → 50 → 300명)에 등급 준비 시간 30일이 없다. 첫 주에 Tier 1 월 상한($250)으로 서비스 전체가 멈출 수 있다.

**권고 (수정)**

- 출시 게이트에 등급을 넣는다: Tier 2는 초대 전, Tier 3은 300명 이전.
- 월 상한 50·75·90% 알림과 상향 신청 런북을 둔다.
- 앱 리미터를 등급의 10분 한도의 60%에 맞춘다. 턴 도중 429를 맞으면 이미 쓴 토큰이 버려지므로 입구에서 거른다.

**불확실성**: 모델별 RPM·TPM 수치는 AI Studio에서만 보인다. 결제 계정 일시 중지가 인프라 프로젝트까지 멈추는지는 문서상 모호하다.

### K2 · 치명 — "최소 비용 안정 운영" 요구와 토폴로지·범위가 맞지 않는다

**발견 1 — 고정비**

- 작은 베타에서도 RDS Multi-AZ, Fargate 3개 서비스의 2개 이상 상주, ALB, NAT, CloudFront/WAF, Cognito가 고정으로 깔린다.
- Codex 스스로 월 $500~1,200으로 잡는다. 같은 규모의 LLM 비용보다 크다.
- 비교: Claude 안은 약 $160/월이다 [추정]. 단가는 공식 GCE·디스크 가격이다(claude-design §15.1).

**발견 2 — 범위**

- 첫 초대 전에 고쳐 써야 하는 것이 많다.
  - 세이브 경로: 동기 `loadGame`·`saveGame`을 비동기 저장소로.
  - API 계약: 모든 변경을 `POST /operations` 202 + 이벤트로.
  - `game-screen.tsx`(1,631줄)의 턴 흐름.
  - lease와 fencing, outbox, RLS.
- 이 새 코드 경로가 원장 정확성 위험의 진원지다. Codex의 출시 기준(lease 만료 뒤 늦은 커밋 차단 등)이 이 위험을 잘 겨누지만, 그 시험이 필요해지는 것 자체가 범위의 비용이다.

**근거 — 300명도 한 호스트로 된다**

- 300명 환산 CPU는 약 4.6 vCPU, 메모리 10~16 GB다 [추정, 실측 기반, claude-design §7].
- 먼저 묶이는 것은 LLM 등급이다(K1). 컴퓨트를 늘려도 처리량이 오르지 않는다.

**권고 (기각 + 2단계 이관)**

- 1단계에서는 Codex의 다중 AZ 컴퓨트, S3 스냅샷, 작업 큐를 쓰지 않는다.
- 2단계 트리거(claude-design §12)가 서면 도입한다.
  - 계획 동시 접속이 32 vCPU의 70%를 넘을 때.
  - 무중단 배포 SLA가 생길 때.
  - 존 장애 RTO 30분이 허용되지 않을 때.
- Codex가 대안으로 든 "Railway + Supabase"는 다음 이유로 1단계 대안이 못 된다.
  - Railway에 서울 리전이 없다(Codex 링크).
  - Supabase daily backup만으로는 세이브 RPO가 24시간이다.

### H1 · 높음 — 법적 출시 게이트가 빠졌다

**발견**: Codex는 "베타 진단 동의·고지"만 다룬다.

**빠진 것** [공식]

- **국외 이전 고지**(개인정보 보호법 제28조의8)
  - `gemini-3.8-flash`는 Vertex에서도 us·eu만 있고 ML 처리도 그 둘이다. 한국 내 처리 선택지가 없다.
  - TypeSafe, Sentry, PostHog, Cloudflare(또는 CloudFront)도 국외다.
- **만 14세 미만 법정대리인 동의**(제22조의2).
- **게임산업법 제21조**: 등급분류, 또는 시험용 게임물 확인(60일·2만 명 이하·무료·표시 의무)이 초대 베타에도 필요하다.

**권고 (수정)**: 게이트 3으로 추가한다(claude-design §10, §11.5). 시험용 확인의 60일 한도는 베타 기간 설계를 직접 제약한다.

### H2 · 높음 — 리비전마다 스냅샷을 쓰는 구조의 쓰기 증폭과 GC

**발견 1 — 무엇이 리비전을 만드나**

- `game_snapshots`는 "작은 본체 + players/contracts 불변 객체"다.
- 그런데 모든 변경이 리비전을 만든다: 턴·전술판 자동 저장·체크포인트·로어북 편집.
- 본체에는 이런 것들이 남는다.
  - lorebook 4.4 MB. Codex 표에 분할이 없다. evidence.md만 언급한다.
  - `matches` 431 KB, `tactics` 343 KB.
  - **끝없이 자라는 `chat`**. 코드에서 `state.chat`을 자르는 곳이 없다 [실측: 검색].

**발견 2 — 얼마나 쓰나** [추정]

- 300명이면 커밋이 초당 약 4건이다(턴 2.8 + 체크포인트 0.6 + 전술판 0.5).
- 본체 1~~5 MB × 4/s = 4~~20 MB/s의 S3 PUT이다.
- PITR 14일 동안 참조를 보호해야 하므로 GC가 지울 수 있는 것이 적다. 보존량이 수백 GB~TB에 이른다.

**권고 (수정)**

- 2단계에서 외부 저장으로 가더라도 다음을 지킨다.
  1. lorebook을 불변 청크로 뺀다.
  2. `chat`을 append-only 페이지로 뺀다. Codex도 "증가량 측정 뒤 분리"를 언급한다. 이 분리를 **필수 전제**로 올린다.
  3. 저장소는 S3가 아니라 PG 청크로 한다(§6).
- 1단계(파일)도 chat 증가가 같은 문제를 일으킨다. 그래서 Claude 안의 B13에 추가한다(§5).

### H3 · 높음 — 대화형 정지 경로가 작업 큐를 지나며 지연이 붙고, 체크포인트 부하 모델이 틀렸다

**발견 1 — 지연**

- 체크포인트와 전술판이 같은 변경 직렬화 경계(작업 큐)를 지난다.
- 한 번에 claim → 스냅샷 로드(S3/DB) → 계산 → 업로드 → CAS 커밋 왕복이 붙는다.
- 실시간 경기는 "말하는 동안 선다"(live-match §8.3). 그래서 정지 → 확정 → 턴의 대기를 감독이 그대로 본다.

**발견 2 — 부하 모델**

- Codex는 "동시 경기 60개가 30초마다 검증, 요청당 0.5 CPU초"로 가정한다.
- 실제 제출은 **시계가 설 때만** 일어난다(live-match §8.1).
- 한 요청은 최대 하프 하나다(`CHECKPOINT_MAX_TICKS` = 경기 시간 60분, `match-flow.ts:484`).
- 그래서 부하는 주기적이지 않고 덩어리다.
  - 실측: 경기 하나 재실행 약 12 CPU초(M2), 체크포인트 처리 최대 11.6 s.
  - 클라우드 vCPU 1.5배 가정이면 하프 하나에 약 9 CPU초 [추정].

**권고 (수정)**

- 체크포인트는 큐 없이 같은 게임 잠금 아래에서 즉시 처리한다. 다중 호스트에서는 lease 소유자가 처리한다.
- CPU 풀은 "덩어리 크기"(하프 단위) 기준으로 잡는다.
- 부하 시험에 하프타임 동시 정지 시나리오를 넣는다.

### H4 · 높음 — runtime cohort의 라우팅과 비용이 정의되지 않았다

**발견**

- 개념(버전 동결, 새 cohort는 새 게임만)은 Claude의 lane과 같다.
- 그러나 다음이 정의되지 않았다.
  - 요청이 그 게임의 runtime에 어떻게 닿는지.
  - 화면 JS와 sim 자산을 cohort별로 어떻게 고정하는지.
  - cohort당 비용.
- Codex 토폴로지에서는 cohort 하나가 web·turn-worker·sim-worker 서비스 셋의 상주 태스크다(최소 2 AZ). 그래서 lane 수만큼 고정비가 곱해진다.

**권고 (수정)**

- Host 기반 lane(`s<N>.play…`)을 쓴다. 한 lane의 페이지·JS·API가 한 빌드에서 나와야 한다.
- 2단계에서도 이전 lane은 최소 크기 하나로 모은다(웹과 워커 겸용).
- lane 수 상한과 일몰 기간은 제품 결정이다.

### M1 · 중간 — 로어북 작업의 재시도 상한이 없다

**발견**

- Codex는 "주기적 DB 스캔으로 재개"하고 "같은 인물의 앞 작업이 실패하면 후속을 앞지르지 않는다"고만 한다.
- 지금 코드는 실패한 작업에 `attempts`만 올리고 상한 없이 남긴다(`lorebook-jobs.ts:54`).
- 주기적 스캔이 붙으면 영구 실패 하나가 **영원히 비용을 낸다.** 같은 인물의 뒤 작업도 영원히 막힌다.

**권고**: 3회 상한, 지수 백오프, `dead` 상태, 운영자 알림. 막힌 인물의 후속 작업 처리 규칙(버리기 또는 병합)을 정한다.

### M2 · 중간 — 기록 스위치와 오류 상세 노출의 결합을 지적하지 않았다

- `errorDetail()`은 `traceEnabled()`가 참일 때 내부 예외 원문을 응답에 싣는다(`turn-runner.ts:296`).
- 운영에서 기록을 켜는 방법이 "그 함수를 참으로"이면 프롬프트 조각과 경로가 사용자에게 샌다.
- Codex 안은 기록을 DB와 S3로 다시 짜므로 이 결합이 사라질 수도 있다. 하지만 계약으로 명시해야 한다.
- **권고**: 기록 저장 스위치와 상세 노출 스위치를 분리하는 것을 출시 게이트 0의 항목으로 둔다.

### M3 · 중간 — 델타 영속화와 재생

- 250 ms 단위로 델타를 `job_events`에 쓰면 턴 하나에 수십 건이다. web이 그 행을 tail하려면 DB 폴링이나 LISTEN이 필요하다.
  - LISTEN은 트랜잭션 풀러와 맞지 않는다.
- 얻는 것은 재접속 뒤의 타이핑 연출이다. 본문은 커밋된 payload에 있다.
- **권고**: 1단계는 상태 폴링 + 최종 payload. 델타 재생은 측정된 이탈 근거가 있을 때만 도입한다.

### M4 · 중간 — 읽기 경로의 비용을 설계하지 않았다

- 지금 GET·선수 카드·리포트는 세이브 전체를 읽는다. load 133 ms + payload 105 ms가 든다 [실측].

- **권고**: revision 키 핫 캐시(읽기 전용 경로)와 뷰 단위 응답. Codex가 언급한 chat 커서 페이지에 동의한다.

## 5. 이 검토로 바뀐 Claude 안의 판단 (최종안 반영 권고)

Codex에서 **채택**할 것:

1. 멱등 키 + **payload 해시**. 같은 id인데 입력이 다르면 409다. `recentRequestIds` 항목에 해시를 함께 둔다.
2. **게임 생성의 멱등성**: `games.creation_request_id UNIQUE`. 지금 `POST /api/games`는 두 번 누르면 게임 둘과 온보딩 LLM 두 번이 생긴다.
3. **삭제 tombstone 재적용**: 백업이나 Litestream 복원 뒤 삭제 기록을 다시 적용한다. 삭제 기록은 별도 append-only로 둔다.
4. 타인의 게임·피드백 id는 **404**(존재를 숨긴다). 이메일 자동 병합 금지.
5. **미보고 사용량은 unknown**이다. 0원이 아니라 보수적 추정값으로 예산에서 뺀다.
6. 인증 응답은 모두 `private, no-store`다. Cloudflare 캐시 규칙은 `/_next/static`에만 둔다.
7. **chat 커서 페이지**와 append-only 분리.
   - 지금 `toPayload`는 보이는 채팅 전체를 매 턴 싣는다. 세이브 본체도 chat 때문에 계속 자란다.
   - 장기 플레이(두 시즌, 약 2,500턴)의 크기를 게이트 1에서 측정한다.
8. 경기 임대에 **epoch**를 둔다. 옛 기기의 지시는 epoch로 거부한다.
9. 운영자 **MFA**, 스테이징과 운영의 키·데이터 분리, 배포 자격 증명 무장기화(GitHub OIDC → GCP Workload Identity).
10. 제품 이벤트는 **커밋 뒤 고유 event id**로 낸다. 클라이언트 클릭을 성공 사실로 쓰지 않는다.

Claude 안 자체 **수정**:

- B13(세이브 크기)에 chat 증가를 추가한다.
- 1단계에서도 디스크 쓰기량 상한 판단은 장기 세이브 측정에 따른다.

Codex 안의 구성 가운데 **기각**할 것 (1단계에 한해서. 2단계 트리거가 서면 재검토):

- RDS Multi-AZ와 Fargate 다중 AZ 상주(K2).
- S3 리비전 스냅샷(H2, §6).
- 델타 영속화와 재생(M3).
- 모든 변경의 작업 큐화 — 체크포인트·전술판 지연(H3).
- Cognito(L1).
- 1단계 RLS(L2).

**PG 청크를 택할 때의 전제** — 코디네이터의 조건에 동의하고 하나를 더한다.

- 논리적 SAVE 형태는 그대로 둔다.
- 게임별 청크 키를 쓰고 전역 중복 제거는 하지 않는다.
- **chat의 append-only 분리가 먼저다.** 그래야 본체 쓰기가 상한을 갖는다.
- daily backup만으로 안정성을 주장하지 않는다. PITR은 필수다.
- 부하 시험으로 WAL 양과 VACUUM을 확인한다.

## 8. 최신 조건(동시 10명 이하 · 무료 우선)과 최신 final-design 검토

> 대상: [final-design.md](final-design.md)(Cloud Run min 0 web·worker + Cloud Tasks·Scheduler + Supabase Free + R2 + 무료 관측)
> 같은 조건에서 Claude의 독립 재평가는 claude-design.md §16에 있다.

### 8.0 결론

**정확성 계약은 수용 가능하다. 오히려 초기 Codex안보다 촘촘하다.**

- job·receipt·fence의 커밋 조건 7개를 한 트랜잭션에 묶는다.
- R2 PUT 뒤에 DB 커밋한다.
- backup pin과 GC를 같은 잠금 순서로 다룬다.
- 복원 뒤 tombstone을 재적용한다.
- 미보고 사용량을 unknown으로 둔다.
- 운영 수집과 UI 노출을 분리한다.

같은 조건의 Claude 독립안(§16)도 이 계약들을 채택한다.

**남은 문제는 다섯 갈래다.**

1. **"모든 쓰기를 Cloud Tasks job으로" + min 0** — 대화형 경로가 매번 큐와 콜드 스타트를 지난다(H1).
   - 대화형 경로: 경기 정지 확정, 전술판 저장, 경기 중 발화.
   - 이것은 AGENTS.md 원칙 4("비용 때문에 경험을 깎지 않는다")와 충돌한다.
2. **화면 projection과 chat이 Supabase Free의 500 MB·egress 5 GB를 잠식한다.** 그 크기를 계산하지 않았다(H2).
3. **DB 손실 RPO 24시간 + 미참조 객체 GC.** DB를 복원하면 R2에 남은 더 최신 세이브를 GC가 지워 버린다. 싸게 RPO를 줄일 길이 있는데 쓰지 않았다(H3).
4. **LLM 비용 예시가 공식 가격·실측 토큰과 무관하다.** Gemini 등급의 월 상한과 결제 계정 정지 위험이 빠졌다(H4, 초기안 K1의 연장).
5. **매분 Scheduler 정리 작업**이 min 0 서비스의 무료 vCPU초를 갉아먹는다. 사실상 DB 휴면 방지 트래픽으로도 동작한다(M1).

### 8.2 발견 사항 (final-design, 중요도순)

#### H1 · 높음 — 대화형 경로가 매번 Cloud Tasks와 min 0 콜드 스타트를 지난다

**발견**

- final §6은 "턴·라인업·협상·메일·checkpoint·승부차기·경기 마감은 같은 job 계약, 매우 짧은 작업도 같은 경계"로 둔다.
- worker는 min 0이고 Cloud Tasks가 깨운다.
- 경기 중 감독이 입력을 시작하면 일이 이렇게 이어진다.
  1. 시계가 선다(live-match §8.3).
  2. checkpoint job이 생긴다: Tasks 전달 → worker 기동 → R2 GET → gunzip·parse·검증 → 구간 재실행 → stringify·gzip → R2 PUT → 커밋.
  3. 한 게임에는 active job이 하나뿐이다. 그래서 checkpoint가 끝나야 턴 job이 다시 같은 경로를 밟는다.

**측정과 추정**

- 로컬 M2, tsx 변환 포함 [실측]
  - 엔진·에이전트 모듈 첫 로드 0.5~1.0 s.
  - 첫 `loadGame` 0.16 s, `stringify` 약 0.16 s.
  - 12.8 MB gzip 0.10 s, gunzip 0.01 s.
  - 프로세스 RSS 430~490 MB.
- Cloud Run 1 vCPU는 이보다 느리다. 컨테이너 기동과 Next 서버 초기화가 더해진다.
- 그래서 유휴 뒤 첫 job에는 **수 초의 콜드 비용**이 붙는다 [추정].
- 하프 하나 재실행은 약 6 CPU초(M2)다. 경기 하나에 12 CPU초.
- **10명 베타는 대부분의 시간이 유휴다.** 그래서 콜드 스타트는 예외가 아니라 기본 경로다.

**권고 (수정)**

- **계약은 같게, 운반은 다르게.**
  - LLM이 없는 짧은 쓰기(checkpoint·전술판·승부차기 한 발·경기 마감 전 확정)는 web 요청 안에서 바로 실행한다. claim → 계산 → 커밋을 한 요청 안에 끝낸다.
  - 같은 `game_jobs`·fence·receipt·revision 조건을 쓴다. 파일 지름길이 아니라 **큐 홉만 생략**하는 것이다.
  - Cloud Tasks에는 LLM job(턴·생성·로어북)만 보낸다.
- 하프 단위 CPU 덩어리는 web에서 worker thread로 격리한다. web 인스턴스는 concurrency를 낮추거나 sim 전용 서비스(min 0)를 둔다.
- Cloud Run startup CPU boost를 적용할지 검토한다(무료 여부는 §8.4의 근거를 따른다).
- "콜드 경로 p95"를 출시 지표로 둔다. 대상은 정지 → 확정 → 턴 첫 델타까지다.

#### H2 · 높음 — projection과 chat이 Supabase Free의 저장 500 MB·egress 5 GB를 잠식한다

**발견**

- final은 "목록·최근 채팅·화면별 read model은 DB의 제한된 projection"을 커밋 트랜잭션에서 갱신한다.
- 지금 화면이 쓰는 전체 뷰(`toPayload`)는 새 게임에서도 423K자이고, UTF-8로는 그보다 크다. `competitions` 하나가 204K자다 [실측].
- 이 뷰를 DB projection으로 두고 턴과 조회마다 읽으면 egress가 이렇게 된다 [추정].
  - 6,000턴 × (커밋 뒤 조회 1~~2회) × 0.4~~0.6 MB ≈ **2.4~7 GB/월** → 무료 5 GB를 넘을 수 있다.
- `state.chat`은 코드에서 잘리지 않는다 [실측: 검색]. chat projection은 게임마다 선형으로 자란다. 2,500턴이면 게임당 수 MB이고, 계정당 게임 2개라면 몇 달 안에 500 MB의 큰 몫이 된다 [추정].

**권고 (수정)**

- DB에는 작은 요약만 둔다: 목록, revision, 마지막 N개 채팅 id.
- 화면 뷰 묶음은 커밋 때 **gzip해서 R2에 따로 둔다**(약 50 KB). R2 egress는 무료다.
- 과거 chat 페이지도 R2로 보관(archive)한다.
- egress와 저장량의 60·80% 알람은 final에 이미 있다. **projection 바이트 예산**을 함께 둔다.

#### H3 · 높음 — DB 복원 뒤 GC가 더 최신 세이브를 지운다. 세이브 RPO를 싸게 줄일 길이 있다

**발견**

- 일일 논리 백업이라 DB RPO는 24시간이다.
- 하지만 그 24시간 동안의 세이브 객체는 R2에 그대로 있다. DB를 어제로 복원하면 그 객체들이 "참조 없음"이 되고, GC 규칙(미참조 + 24시간 경과)이 그대로 지운다.
- 그러면 되살릴 수 있었던 진행이 영구 손실된다.

**권고 (수정)**

1. 커밋 뒤 R2에 작은 **commit marker**를 쓴다. 내용: `game_id`, revision, snapshot key·sha, job id, receipt keys.
   - best-effort로 쓰고 outbox로 재시도한다.
2. 복원 절차는 다음 순서다.
   1. GC를 동결한다.
   2. 게임마다 marker의 최고 revision으로 `games.snapshot_id`를 **롤포워드**한다.
   3. receipt를 재구성한다.
   4. 그다음 tombstone을 재적용한다.
3. ~~그러면 세이브 RPO는 24시간에서 수 분으로 준다~~ → §8.6에서 정정했다. 자동 롤포워드는 계정·소유권의 원자성을 재구성하지 못한다. 그래서 설계 보장은 24시간이고, marker는 운영자 승인의 반자동 구출 수단이다.
4. 주 1회 운영자 수동 다운로드는 잊기 쉽다. 다른 계정의 무료 저장소로 **자동 복제**하는 쪽을 권한다.
   - 예: GCP 무료 Cloud Storage(가능 여부는 §8.4).

**확인 필요**

- Cloud Run에서 Supabase Free로 가는 `pg_dump` 경로: 세션 풀러를 쓸지, IPv6 직접 연결을 쓸지.
- 덤프에 `auth` 스키마를 포함하는 권한.

final도 "공식 복원 절차를 고정 CLI로 시험"한다고 적었다. 이 둘을 게이트 항목으로 명시하는 것을 권한다.

#### H4 · 높음 — LLM 비용과 Gemini 등급 위험이 빠졌다

**발견 1 — 비용 예시**

- final §13은 "턴당 $0.01·$0.05·$0.10, 6,000턴이면 월 $60~600"으로 적고 "현재 모델 가격 아님"이라고 단서를 단다.

| 계산                                 | 턴당                 | 6,000턴 기준 월  |
| ------------------------------------ | -------------------- | ---------------- |
| 공식 가격 × 실측 토큰, 2026년 [추정] | 약 $0.019 **(하한)** | **약 $114 이상** |
| 사고 토큰 500~2,000/턴 가정, 2026년  | $0.021~0.026         | $126~156         |
| 같은 계산(하한), 2027-01-01부터      | 약 $0.037            | 약 $222 이상     |
| (참고) 실패·온보딩 추가분            | —                    | 10~20%           |

- 실측 토큰: 턴당 Flash 입력 28.5k(캐시 24%)·출력 450.
- **출력 450에는 사고 토큰이 빠져 있다**(§8.6). 그래서 과거 기록 기반 비용은 총비용이 아니라 하한 참고값이다.
- 가격 출처는 claude-design §1.3과 §8.1이다.

**발견 2 — 등급 상한**

- Tier 1의 월 상한은 $250이다. 닿으면 연결된 프로젝트의 Gemini API가 멈춘다 [공식 문구 해석].
- 2027년 가격에서는 10명 베타도 상한에 다가가고, 사고 토큰을 넣으면 넘을 수 있다.
- 인프라 지출이 거의 0이라 Tier 2 승급 조건($100 누계 + 3일)도 LLM 지출로만 채워진다.

**발견 3 — Gemini 무료 등급**

- Gemini **무료 등급**은 콘텐츠를 제품 개선에 쓰고 사람이 검토할 수 있다 [공식, terms]. "무료 우선"이 LLM까지 번지면 사용자의 자유 입력이 그 조건에 놓인다.
- final의 "무료 tier 모델로 치환하지 않음"은 맞다. **이유(데이터 사용 조건)를 명시**할 것을 권한다.

**권고**

- 비용 표를 공식 가격 × 실측 토큰으로 바꾸되 하한으로 표시한다. 사고 토큰 계측(B14)을 출시 차단 항목으로 둔다.
- ~~Tier 2 도달을 출시 게이트에 넣는다~~ → **예상 월 Gemini 지출(사고 토큰 포함)이 Tier 1 상한의 60%($150)를 넘을 전망이면 승급**한다(§8.6에서 코디네이터 판단을 수용해 수치 조건으로 바꿨다).
- 월 상한 50·75·90% 알림을 둔다.

#### M1 · 중간 — 매분 Scheduler 정리 작업의 비용과 휴면 방지 효과

**발견 1 — 비용**

- 매분 호출이면 월 43,200회다. min 0이면 매 호출이 콜드 스타트이거나 최소 과금 구간을 낸다.
- 1회 0.5~~1 vCPU초라면 월 22k~~43k vCPU초다. 무료 180k의 12~24%다 [추정].

**발견 2 — 휴면 방지 효과**

- 매분 DB를 조회하면 Supabase 휴면 조건을 사실상 막는다. final의 "휴면 방지용 가짜 트래픽에 의존하지 않는다"와 결과가 같아진다. 실제 일이긴 하다.

**권고**

- 정리는 job 제출·완료 때 같은 요청 안에서 **기회적으로** 하고, Scheduler는 5~10분 간격으로 둔다.
- 휴면 방지 효과는 문서에 사실로 적는다.

#### M2 · 중간 — 지역

- final은 Cloud Run과 Supabase를 싱가포르에 둔다.
- 도쿄(`asia-northeast1`)는 한국에서 더 가깝다. Cloud Run Tier 1이고 Supabase 리전도 있다 [공식 — Cloud Run locations · Supabase regions].
- 싱가포르를 고른 이유(무료량 계산 등)가 없다면 도쿄를 권한다. 무료량 적용 방식은 §8.4를 따른다.

#### M3 · 중간 — 작은 조작마다 세이브 전체를 다시 쓴다

**발견**

- 전술판 자동 저장(3초 유휴)과 로어북 patch 하나도 전체 GameState를 stringify → gzip → R2 PUT으로 처리한다.
  - 12.8 MB, gzip 1.34 MB이고 M2 기준 약 0.26 s다.
- GCP → R2 전송은 GCP 인터넷 egress로 과금된다(final도 인정한다).
- 6,000턴 + 경기 정지·전술판 수천 회면 월 **10 GB 이상**의 PUT이다 [추정].

**권고**

- 전술판 저장은 다음 턴에 묶는다(경기 중 전술판 조작은 이미 그렇게 묶인다). 아니면 유휴 시간을 늘린다.
- players·contracts·lorebook 청크화(final은 "확장 최적화")를 **조기 선택지**로 올린다.
  - 바뀌지 않은 청크는 다시 PUT하지 않는다.
  - 본체는 약 1 MB raw(gzip 수백 KB 이하)로 준다 [추정, evidence 표 기준].
- "무료"의 의미에 GCP egress 소액이 들어간다는 것을 비용 표에 적는다.

#### M4 · 중간 — 실행 슬롯과 무료량 산정이 실측보다 비관적이다 (방향은 안전)

- final은 job 평균 30~60 s로 잡는다. 실측 턴은 평균 9.0 s, p90 15 s, p99 29 s다.
- 6,000턴을 다시 계산하면 이렇다 [추정].
  - 턴: 6,000 × (9 s + 오버헤드 2~~4 s) × 1 vCPU ≈ 66k~~78k vCPU초, 2 GiB면 132k~156k GiB초.
  - 경기 검증·web·정리 작업을 더해도 **무료 180k vCPU초·360k GiB초 안**이다.
  - 단 M1의 매분 작업이 여유를 크게 먹는다.
- 슬롯 4개는 충분하다.

#### L1 · 낮음

- 1~2초 폴링은 10명 규모에서 합리적이다. LLM을 기다리는 동안 web이 같이 과금되지 않는다.
- worker 2 GiB · concurrency 2는 실측 RSS(약 0.5 GB) + 상태 17 MB × 2에 맞다.
- 이전 cohort를 min 0으로 두는 방식은 상주비가 없다. 한 cohort의 페이지·JS·API를 같은 빌드로 묶는 Claude의 lane 조건(§3.3)과 함께 적용한다.
- Supabase Before User Created hook으로 초대를 서버에서 강제하는 것은 좋다. Kakao는 Supabase가 지원하므로 나중에 추가하면 된다.

### 8.5 최종 합성 권고 (최신 조건)

**골격** — final 유지

- Cloud Run min 0(web·worker 분리) + Cloud Tasks(LLM job) + Supabase Free(Auth·원장) + R2(스냅샷).
- 포인터 CAS, receipt, fence, outbox.

**final에 반영할 수정 (Claude 권고)**

1. 지역을 **도쿄**로 바꾼다. Cloud Run과 Supabase 모두(§8.2 M2, §8.4).
2. **짧은 쓰기는 web 요청 안에서** 같은 계약으로 실행한다. Tasks는 LLM job 전용(H1).
3. 화면 projection과 과거 chat을 **R2**로 옮긴다. DB에는 작은 요약만 둔다(H2).
4. **R2 commit marker**를 반자동 구출용으로 남긴다(자동 롤포워드는 §8.6에서 철회). 복원할 때 GC를 동결하고 미참조 객체를 격리한다. 다른 계정으로 자동 복제한다(H3).
5. LLM 비용 표를 **공식 가격 × 실측 토큰의 하한**으로 둔다(턴당 약 $0.019 이상, 6,000턴이면 월 약 $114 이상 — 사고 토큰을 빼고 센 값, §8.6). 사고 토큰 계측을 출시 차단 항목으로 둔다. 월 상한·10분 한도 알림과 수치 기반 승급 조건을 둔다. 무료 등급을 쓰지 않는 이유(데이터 사용)를 명시한다(H4).
6. 정리 작업은 기회적 실행 + 5~10분 Scheduler로 한다. 휴면 방지 효과는 사실로 적는다(M1).
7. 전술판 자동 저장은 다음 턴에 묶는다. 청크화는 조기 선택지로 둔다(M3).
8. 무료량 산정은 실측(평균 9 s)으로 다시 한다. 도쿄에서 6,000턴/월은 무료 vCPU초의 약 53%다(M4, claude-design §16.2).

**Claude 독립안에서 유지할 것**

- 실측 묶음(단위 정정 포함).
- 로어북 재시도 상한(B7).
- 기록·상세 노출 분리(B3).
- `x-gaffer-build`와 cohort 단위 동일 빌드.
- 문서 불일치 보고: live-match §8.4 임대, models.md §1-1 락 회수, `persistence.ts:49` 주석, `live-match.md:840`의 SAVE_VERSION 18.

**법령** — 코디네이터 방침대로 최종 기술 설계에서는 빼되, **공개 전 정책 확인 목록**으로 따로 남기기를 권한다.

- 게임 등급분류 또는 시험용 게임물 확인. 시험용은 60일·2만 명·무료 조건이라 베타 기간 설계를 직접 제약한다.
- 국외 이전 고지(Gemini는 한국 내 처리 선택지가 없다).
- 만 14세 미만 정책.

**남은 불확실성** (최신 조건)

1. Cloud Run에서 Next·엔진 이미지가 실제로 얼마나 늦게 뜨는가(콜드 스타트). 로컬 근사는 모듈 로드 0.5~1.0 s뿐이다.
2. `db dump`가 auth 스키마를 포함하는 권한과 경로(세션 풀러 또는 IPv6).
3. GCP → R2 전송 단가(이번에 공식 수치로 확정하지 못했다).
4. Neon 콜드 재기동 지연과 Neon Auth의 초대·Kakao 지원.
5. 장기 플레이 세이브의 크기 증가. 스냅샷 PUT 바이트와 무료 저장량이 여기에 달려 있다.
6. 사고 토큰의 실제 양(`thinking_level: low`). 과거 기록에는 남아 있지 않아 유료 soak에서만 정해진다.

   - §6에서 이미 즉시 경로를 기본으로 정했다. 그래서 "즉시 경로의 p95 2초" 목표로 고치면 된다.
3. **콜드 경로가 두 번 겹칠 수 있다.** web(min 0) → sim(min 0)이라 경기 정지 한 번에 콜드 스타트가 둘 겹칠 수 있다. §15의 "worst-case burst p95와 UI 정지 체감" 지표에 **유휴 30분 뒤 첫 정지**를 시나리오로 명시하기를 권한다.
4. **백업 연결 경로.** exported snapshot을 쓰는 dump는 세션 연결이 필요하다. Supabase Free에서 Cloud Run이 세션 풀러로 갈지, IPv6 직접 연결로 갈지와 `auth` 스키마 덤프 권한을 §15 "배포/복원" 검증 항목에 이름으로 적기를 권한다.
5. **web 1 GiB.**
   - 즉시 경로가 web에서 스냅샷을 로드·검증·gzip한다.
   - 실측: 프로세스 RSS 약 0.43~0.49 GB, 상태 하나 17 MB, 12.8 MB JSON 파싱의 일시 피크.
   - concurrency 20에서 동시 즉시 커밋 몇 개가 겹치는 경우를 최대 메모리 검증에 넣는다.
6. **LLM 비용의 크기 감.**
   - final은 민감도 예시($0.01~0.10/턴)만 남기고, Claude의 $0.019/턴은 총비용으로 쓰지 않았다(정당하다).
   - 사용자가 예산 감을 잡도록 "공식 가격 × 실측 입력 토큰의 **하한** 약 $114/6,000턴(2026년, 사고 토큰 제외)"을 하한 참고값으로 한 줄 병기하기를 권한다. 결정은 코디네이터 몫이다.
