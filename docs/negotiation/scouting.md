# 스카우팅 — 의뢰, 조사, 보고

스카우팅은 감독이 선수에 대해 판단할 근거를 얻는 과정이다. 메인 GM이 의뢰를
접수하면 Jev가 **무엇을, 어느 정도까지, 언제 보고할 수 있는지** 평가한다.
예정일이 되면 이벤트가 실행되고, 확보한 근거를 Jev가 평가해 보고서로 남긴다.
메인 GM은 스카우트의 말로 결과를 전달하고 영입·기용에 관한 다음 대화를 이어 간다.

스카우팅은 **negotiation 도메인**이 소유한다. 협상 GM은 실제 거래 상대와 연락할 때
참여하며 내부 조사마다 부르지 않는다.

## 1. 감독이 의뢰하는 것

“이 선수를 알아봐”, “왼발로 전진 패스하는 센터백을 찾아줘”, “지난 후보들의 부상
이력을 더 확인해줘”를 같은 의뢰 흐름으로 다룬다. 특정 선수 조사·후보 탐색·비교·추가
조사는 대상과 질문이 다를 뿐 별도 파견 시스템이 아니다.

의뢰에는 감독의 원문, 대상 또는 탐색 조건, 알고 싶은 점, 우선순위와 희망 기한을
남긴다. 기존 보고서에서 이어지는 조사라면 그 보고서를 참조한다. 희망 기한은 감독의
요청이며 조사 완료를 보장하는 날짜가 아니다.

- **조회**는 이미 아는 사실과 보고서를 읽는다. 시간이 흐르거나 새 지식이 생기지 않는다.
- **스카우팅**은 관측·조사할 일을 계획하고 이후 보고서를 받는다.
- **접촉**은 구단·선수·에이전트에게 실제로 문의하거나 제안하는 행동이다.
  감독이 요청하거나 위임한 경우 [협상 흐름](transfer.md)으로 연결한다.

선수를 조사하는 것만으로 관심 표명·접촉·제안이 자동 발생하지 않는다.

## 2. 하나의 의뢰가 진행되는 길

| 단계        | 담당                         | 남기는 것                                        |
| ----------- | ---------------------------- | ------------------------------------------------ |
| 의뢰        | 메인 GM의 `request_scouting` | 원문·대상·질문·기한                              |
| 계획 평가   | Jev                          | 가능한 범위·예상 정보 수준·소요 일수·보고서 구성 |
| 예약        | 검증된 코어 명령             | 조사 계획·예정일·보고 이벤트                     |
| 예정일 도달 | app의 이벤트 실행            | 해당 시점까지 확보한 근거                        |
| 보고 평가   | Jev와 코어 검증              | 확인한 사실·추정·판단할 수 없는 점이 담긴 보고서 |
| 전달        | 메인 GM                      | 보고서 카드와 스카우트의 설명·후속 대화          |

예를 들어 급히 후보를 요청하면 공개 경기 자료 중심의 빠른 보고가 가능할 수 있다.
장기 성장이나 특정 역할 적합성까지 확인하려면 다른 표본과 시간이 필요할 수 있다.
이 차이는 요청·일정·자료 접근성에서 평가하며 유형별 고정 일수로 정하지 않는다.

## 3. Jev가 계획하는 범위와 시점

계획 평가는 의뢰, 이미 알고 있는 선수 정보, 기존 보고서, 접근 가능한 경기·자료,
담당 스태프와 진행 중인 조사, 감독의 우선순위를 읽는다. 비공개 참 능력치·잠재력을
읽고 조사 대상을 골라 주지 않는다.

계획의 결과는 다음을 함께 설명할 수 있어야 한다.

| 항목           | 의미                                                          |
| -------------- | ------------------------------------------------------------- |
| 조사 범위      | 대상·탐색 범위와 답할 질문, 이번 조사에서 다루지 못하는 질문  |
| 관측 근거      | 이용할 수 있는 경기·공개 기록·기존 보고서와 접근상의 제약     |
| 예상 정보 수준 | 항목별로 확인·추정 가능한 범위와 남을 불확실성                |
| 일정           | 시작 가능한 때, 필요한 일수, 보고 예정일                      |
| 보고 내용      | 개별 분석·후보 목록·비교·특정 의문 확인 등 의뢰에 필요한 구성 |
| 진행 가능 여부 | 진행, 조건 조정 필요, 조사 불가와 그 근거                     |

감독의 지시 범위 안에서 실행 가능한 계획은 바로 예약한다. 대상을 바꾸거나 기한·범위를
중요하게 바꿔야 한다면 대안을 전달하고 의뢰를 보류한다. 못 나간 의뢰도 기록으로 남는다.
담당자가 바쁘다는 이유를 임의의 ‘동시 3건’으로 대체하거나 일주일 뒤 지우지 않는다.

**정확도는 항목별 예상 정밀도와 근거의 충실도다.** Jev의 응답 확률을 보고서의
정확도 확률로 표시하지 않는다. “정확도 90%” 같은 보정되지 않은 보장 대신 무엇을
확인할 수 있고 무엇이 추정으로 남는지 알려 준다. 서로 다른 능력·역할·성장 전망에
하나의 정확도 점수를 붙이지 않는다.

소요 일수는 Jev가 맥락에서 평가한다. 코어는 유효한 날짜와 정수 일수, 과거 예약 금지,
실재하는 관측 일정·참조를 검증한다. 이미 확보한 자료만으로 가능한 조사는 당일 보고도
가능하지만 미래 경기의 정보를 미리 사용하지 못한다. 기술적 입력 한도는 조사 기간이나
후보 수를 정하는 밸런스 상수로 사용하지 않는다.

## 4. 보고 예정일의 이벤트

조사 예약은 협상 후속 일과 **같은 날짜 이벤트 실행 기반**을 사용한다. 별도 스카우팅
시계나 매일 도는 LLM을 만들지 않는다. 순수 tick은 기한 도달을 알리고 app이 Jev를
호출한다. 날짜를 여러 날 넘겨도 중간 예정일을 순서대로 처리한다.

1. app이 의뢰 ID·계획 버전·예정일로 이벤트의 유효성을 확인한다.
2. 예정일까지 실제로 접근 가능한 관측 근거를 고정한다. 예정일 이후 사실은 섞지 않는다.
3. Jev가 의뢰의 질문에 따라 근거를 평가한다.
4. 코어가 대상·출처·수치 범위·기록 일관성을 검증하고 보고서와 완료 상태를 함께 저장한다.
5. 그 날짜에 도달한 턴에 도착 사실과 보고서를 전달한다. 메인 GM이 설명하기 전에 같은
   보고서 내용을 입력으로 받는다. 경기 중이면 알림과 보고서는 보존하고 대화는 첫 평시 턴에 잇는다.

관측하려던 선수가 결장했거나 자료를 구할 수 없었다면 예정일에 그 한계까지 보고한다.
당초 정확도를 맞추려고 관측을 꾸미거나 무기한 연장하지 않는다. 추가 조사가 필요하면
가능한 다음 계획을 제시하되 감독의 요청·위임 없이 새 의뢰를 실행하지 않는다.

기술적 호출 실패와 조사 결과 부족은 다르다. 호출 실패는 오류·재시도 상태로 남기며
‘정보 없음’ 보고서로 성공 처리하지 않는다. 재시도는 같은 근거와 이벤트 ID를 사용한다.
취소·재계획된 버전의 이벤트는 결과를 적용하지 않고, 중복 실행도 보고서를 두 번 만들지 않는다.
도착한 턴의 전달에 실패하면 완료된 보고서를 보관하고 다음 전달 시 다시 평가하지 않는다.

GM 서술 전에 날짜 진행과 도래 평가가 끝난 상태를 체크포인트로 잡는다. 서술이 실패하면
감독 원문과 이 체크포인트를 저장하고 미전달 보고서 목록을 유지한다. 화면은 저장 상태를
다시 읽으며 같은 시간 이동이나 제안을 자동 재전송하지 않는다. GM 도구로 새로 처리한
스카우팅은 같은 날짜·국면의 체크포인트에 의뢰·보고서·전달 대기 목록만 반영한다.
뒤이어 실패한 GM의 다른 변경이나 미완성 답변은 이 저장에 섞지 않는다.

## 5. 보고서에 남기는 정보

보고서는 **작성 시점의 관측 기록**이다. 선수의 현재 상태를 매번 조회해 과거 보고서의
내용을 바꾸지 않는다. 조사 대상이 이후 이적·은퇴해도 당시 이름·소속·관측과 출처는 남는다.

- 의뢰한 질문, 조사 기간과 작성일, 자료 출처와 근거 기준일.
- 확인된 사실과 근거가 있는 추정. 항목마다 근거·불확실성·판단 보류를 구분한다.
- 후보별 장점·제약과 감독의 요구에 맞는지에 대한 평가. 적합하지 않은 이유도 남긴다.
- 답하지 못한 질문과 추가 확인이 필요한 사항.
- 관련 선수·기존 보고서·실제 연락 기록의 참조.

추천 후보는 조건을 충족하고 설명할 근거가 있는 만큼이다. 다섯 명을 채우려고 무관한
선수를 넣지 않으며 결과가 없어도 유효한 보고다. 조사한 후보의 부적합·판단 보류도
보고서에 보존하되 화면에서는 별도로 펼쳐 확인한다. 관측 종합 순으로 자동 추천하지 않고
감독이 원하는 역할·전술·기한·재정 조건에 비추어 Jev가 평가한다. 탐색·필터·정렬도
공개·관측 정보만 사용한다. 넓은 탐색을 나누어 처리할 때는 실제 조사한 범위를 기록한다.

**예상과 실제의 차이도 정보다.** 계획에서 약속한 항목을 실제 보고서에서 확인했는지
표시한다. 재조사 횟수만큼 오차가 자동으로 줄어들지 않으며, 근거가 충돌하면 불확실성이
커질 수도 있다. 새 보고서는 이전 것을 지우지 않고 달라진 판단과 근거를 함께 보여 준다.

능력·성장 전망은 관측 근거가 허용하는 추정만 저장한다. 관측 데이터의 표시 규약은
[선수 문서](../common/player.md#9-안개--관측-가능성-히든-능력치의-대체물)를 공유하고,
성장 가능성은 같은 여섯 단계와 ‘판단 보류’를 사용한다. 잠재력 참값을 조회해 추정을
보정하거나 관측의 정확도를 보장하지 않는다. 보고서가 실제 선수 능력치를 바꾸지도 않는다.

최근 기록 이적료는 당시 거래의 참고값이며 현재 구단의 요구 가격이 아니다. 기록이
없으면 금액을 추정해 채우지 않는다. 현 주급 역시 새 계약의 요구 조건이 아니다.
실제 연락에서 확인된 조건만 상대의 요구로 표시하고 해당 교환을 참조한다.

## 6. 스킬과 모델의 경계

| 호출                        | 계약                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| 메인 GM `request_scouting`  | 신규 의뢰·기존 의뢰의 변경·취소. 원문 출처와 대상, 질문, 선택적 기한·기존 의뢰 참조를 전달 |
| 의뢰 처리 중 Jev 계획 평가  | 조사 가능성·범위·예상 정보 수준·일정을 평가하는 내부 호출                                  |
| 도래 이벤트의 Jev 보고 평가 | 확보한 근거로 선수·후보를 평가하는 내부 호출                                               |
| 읽기 전용 조회              | 의뢰 진행 상태와 보관 보고서를 ID 또는 선수·조건으로 조회. 새 조사나 평가를 실행하지 않음  |

`market_orders`는 스카우팅을 별도로 실행하지 않는다. 두 Jev 평가는 GM이 직접
호출하는 별도 스킬이 아니라 `request_scouting`과 이벤트가 사용하는 도메인 평가다.
별도 스카우팅 GM도 두지 않는다. 메인 GM이 검증된 평가를 스카우트의 말로 전달한다.

현재 Jev 어댑터의 Choice·Score·Noul 기반 타입 평가와 도메인 어댑터를 사용한다.
질문·후보·근거 참조·수치 탐색으로 계획과 평가를 구성하고 Zod로 검증한다. Jev에 임의
JSON이나 보고서 산문 생성 기능이 있다고 가정하지 않는다. 평가 사유는 사용한 근거와
연결해 전달하고, GM의 문장은 그 범위를 넘는 사실이나 수치를 추가할 수 없다.
계획과 보고 평가는 `config/llm.yml`의 `scouting` 역할을 사용한다([모델 설정](../common/llm/models.md)).

보고서의 구조화된 평가가 원본이며 카드·조회·GM 입력이 이를 함께 읽는다. 전달 문장은
채팅 기록에 남긴다. 재열람을 위해 별도 추천문 생성 호출이나 보고서 사본을 만들지 않는다.

## 7. 저장과 도메인 연결

저장의 중심은 **의뢰와 보고서**다. 의뢰에 현재 계획·버전·상태·예정 이벤트 참조를,
보고서에 시점별 관측·평가·근거를 둔다. 이벤트의 실행 상태와 전달 여부는 구분한다.
미전달 목록은 보고서 ID만 가리키고, 화면 한 번에 보여 줄 수 있는 수를 넘었다고
보고서를 삭제하지 않는다. 완료·취소된 의뢰도 이력으로 조회할 수 있다.

| 계층        | 책임                                                               |
| ----------- | ------------------------------------------------------------------ |
| common      | 선수·팀·인물 ID와 실제 상태, 공통 관측 표시 타입·날짜              |
| negotiation | 의뢰·조사 계획·보고서 스키마, Jev 질문과 평가, 검증·예약·완료 명령 |
| story       | 메인 GM의 의뢰 접수와 스카우트 장면, 전달받은 사실을 서사로 연결   |
| app         | 자료와 도메인 조회 조립, 날짜 이벤트와 Jev 실행, 보고서 전달       |

의존성은 `common → {story, negotiation, match} → app`이다. negotiation이 경기
엔진이나 story GM을 직접 호출하지 않고, app이 필요한 경기 기록·스태프 정보를 전달한다.
common에는 스카우팅 실행이나 개별 도메인을 읽는 조회가 들어가지 않는다.

내부 조사는 상대와의 협상 테이블이 아니다. 보고서를 보고 접촉하면 해당 구단 또는
에이전트의 기존 테이블을 찾아 연결하며, 대면·통화·제안서 기록은 그 테이블에 남는다.
보고서는 여러 거래에서 참조할 수 있지만 거래 조건·승인·약속을 복사해서 소유하지 않는다.

## 8. 구현 검증의 핵심

- 예정일을 지나거나 당일 보고를 요청해도 이벤트가 누락·중복되지 않는다.
- 변경·취소된 계획과 늦게 반환된 평가는 현재 의뢰를 덮어쓰지 않는다.
- 실패 후 재시도·저장 복원·시즌 전환에도 근거 시점과 보고서 ID를 유지한다.
- 숨은 참값이 탐색·정렬·추정·GM 입력으로 새지 않는다.
- 관측 부족과 기술 오류를 구분하며, 계획의 예상 정밀도를 관측 결과로 간주하지 않는다.
- 카드·조회·GM 입력은 같은 보고서를 읽고, 이후 선수 상태 변화가 과거 보고서를 바꾸지 않는다.

고정 소요 일수·파견 슬롯·후보 수·재조사 보너스·보고서 삭제 한도를 밸런스 규칙으로
두지 않는다. 품질 평가는 근거 일치·기한의 타당성·후보 적합성으로 수행하고, 저장·날짜·
중복 방지 등의 불변식은 모델 없이 검증한다.

실패 시 조사 결과만 따로 저장할 때는 고정된 공개 근거를 턴 시작 체크포인트에서 다시 확인한다. 같은 턴의 다른 명령이 바꾼 계약·소속 등 미저장 사실에 의존하는 새 보고서는 분리 저장하지 않는다. 이미 확정한 날짜 진행과 도착 보고서 체크포인트는 유지한다.
