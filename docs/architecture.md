# story-fm의 책임 구조

story-fm은 자연어로 감독이 되어 살아가는 게임이다. 재미의 중심은 세 가지다.

1. **구단의 일상과 서사** — 메인 GM이 훈련·면담·기자회견을 진행한다. 인물의 기억과 관계, 감독의 선택이 다음 장면에 이어진다.
2. **협상과 운영** — 협상 GM이 구단·선수·에이전트와의 대면·연락을 진행한다. Jev가 조건을 평가하고 계약·약속·재정은 검증된 장부로 남는다.
3. **실시간 경기** — 선수와 전술이 공간 시뮬레이터에서 경쟁한다. 감독은 자유롭게 개입하고, 검증된 지시가 다음 구간의 플레이를 바꾼다.

## 책임의 경계

AI는 의미를 해석하고 인물의 반응과 이야기를 판단한다. 코어는 대상의 존재, 소유권,
날짜, 계약, 지출 가능 여부, 수치의 범위와 누계를 검증한다. 자유 텍스트로 장부를
바꾸지 않으며, 검증을 통과한 구조적 출력만 결정적 명령으로 반영한다.

선수 능력치·포지션·역할·체력·적응도·폼은 감독이 판단할 수 있는 정보다.
경기 결과와 재정의 사실은 모델이 서술한 결과가 아니라 시뮬레이션과 원장이 정한다.

## 기억과 이야기

최근 대화, 지난 일 요약, 열린 이야기, 인물별 기억과 관계가 서사의 지속성을 담당한다.
끝나지 않은 이야기의 전개와 마무리는 GM이 맥락에서 판단한다. 코어는 부상·계약·
경기 결과처럼 이미 갖고 있는 사실을 별도 발단·고조·절정 장부로 다시 저장하지 않는다.
협상과 약속의 현재 상태는 각 원장이 유일한 출처다.

대화 반응은 GM의 판정이다. 코어는 그 반응의 수치 효과와 하루·주간 누계를 제한한다.
선수의 성격, 최근 경기, 불만과 관계를 별도 수용성 점수로 합산해 판정을 덮어쓰지 않는다.

## 거래와 장부

[선수 거래 명세](negotiation/transfer.md)는 대면·통화·제안서를 하나의 협상 경험으로
다룬다. 메인 GM은 관리 지시와 협상 연결을 맡고, negotiation-gm은 당사자와의 교환을
주관한다. Jev는 맥락에 맞는 조건·상대 입장·선택적 후속 일을 평가한다. 코어는
평가를 성사 확률이나 고정 가격 배수로 덮어쓰지 않고 권한·계약·원장을 검증한다.

같은 상대의 협상 테이블에 대면·통화·제안서 기록을 함께 남기고 선수별 거래 조건은 구별한다. 각 교환은 조건 버전과 승인·평가·예약을
참조하며, UI 국면 변경으로 사라지지 않는다. 계약·지급·약속은 원자적으로 확정한다.
기존 회계 경로 `settlePlayerFee`처럼 같은 장부 규칙은 유저·AI 거래가 함께 사용한다.

app은 예정일 도래 시 해당 협상을 재개하고, 확정 기록과 협상 GM 요약을 story에
전달한다. story는 공개 범위 안에서 장면과 관계를 이어 간다. 요약은 계약의 또 다른
원본이 아니고, 일상 GM이나 순수 tick에 별도 상대 판정기를 두지 않는다.

## 조사와 보고

[스카우팅](negotiation/scouting.md)은 negotiation의 책임이다. 메인 GM의
`request_scouting`으로 요청을 받고, Jev가 조사 범위·예상 정보 수준·일정을 평가한다.
app은 예정일에 확보한 근거를 조립하고 Jev 보고 평가를 호출한다. 코어가 검증·저장한
같은 보고서를 카드·조회·메인 GM이 읽는다. 조사마다 협상 GM이나 별도 스카우트 GM을
호출하지 않으며 실제 상대 접촉부터 협상 테이블로 연결한다.

common은 실제 선수·팀 정보와 관측의 표시 규약만 소유한다. 조사 기록은 negotiation에
두고 app이 match의 경기 기록과 story의 스태프 맥락을 전달한다. 도메인끼리 직접
호출하지 않는다. 조사 예약은 협상 후속 이벤트와 날짜 실행 기반을 공유한다.

## 상태와 세계 생성

`common/core/state.ts`는 상태의 형태, 조회와 작은 장부 연산을 소유한다. 세계 생성·일정
편성·경기 진행·선수단 선택을 import하지 않는다. 대표팀 소집과 부상·징계에 따른
현재 가용성도 저장된 사실을 읽는 조회이며, 대표팀 시뮬레이션을 호출하지 않는다.

새 게임 생성은 `app/create-game.ts`가 카탈로그·선수 생성·대회·훈련·인물 초기화를
조립한다. 포메이션 평가와 선발·벤치 선택은 `match/squad/selection.ts`의 한 규칙을
초기 편성과 시즌 중 재편성이 함께 사용한다. 패키지 공개 API는 `index.ts`가
재노출하며, 엔진 내부에서는 소유 모듈을 직접 import한다.

## 보드와 사회적 반응

감독과 보드가 협의한 기대와 최근 평가는 `boardAgenda`에 남는다. GM이 맥락에서 기대를
협의하고 평가하며, 코어는 신뢰 변화의 범위와 고용 상태 전이를 검증한다.
회견·면담도 같은 반응 장부를 사용한다. 태도별 효과표와 원형별 보드 과제,
다년 비전의 점수 합산과 보드 압력 카운터는 두지 않는다.
체급별 순위는 AI 구단 운영과 감독 영입의 경쟁 기준이다. 현재 보드와 합의한 기대와
구분한다. 감독 계약 만료 90일 이내의 갱신 제안 여부도 보드 장면에서 명시적으로 판단한다.
세부 계약은 [보드와 공개 반응](story/board.md)을 따른다.

## 도메인과 조립 계층

| 도메인        | 소유하는 일                                                | 주요 정보                               |
| ------------- | ---------------------------------------------------------- | --------------------------------------- |
| `story`       | 메인 GM의 일상·훈련·회견, 인물 기억·관계, 보드 기대와 평가 | 장면, 반응, 심경, 훈련, 경력            |
| `negotiation` | 협상 GM의 설득, 선수·감독·스태프 계약, 재정·약속           | 제안, 계약, 지급, 요청, 약속            |
| `match`       | 경기 GM, 전술·선발, 실시간 진행·결과, 대회 운영            | 전술, 공간 상태, 사건 원장, 일정·순위   |
| `common`      | 여러 경험이 함께 쓰는 선수·팀 정보와 기초 규칙             | 신원, 능력·몸 상태, 카탈로그, 날짜·난수 |

`app`은 네 도메인을 조립한다. 새 게임 생성, 하루·시즌 진행, 저장 스키마,
통합 화면과 GM 스냅샷은 여러 도메인을 연결하므로 이 계층에 있다.
도메인의 판단 규칙을 `app`이나 `common`에 다시 작성하지 않는다.

실행 환경의 경계도 유지한다. `packages/domain`은 브라우저에서 안전한 모델과 순수
규칙, `packages/engine`은 상태 전이, `packages/agents`는 모델 호출을 맡으며 각 패키지
안에서 같은 도메인 이름으로 파일을 찾는다. `packages/sim`은 `match` 전용 공간 코어,
`packages/llm`은 공통 제공자 기반이다. 웹의 도메인별 화면·클라이언트 코드는
`apps/web/domains`에 있고, Next 라우트는 API와 URL 경계를 담당한다.

공통 선수·팀 정보는 복제하지 않는다. 경기 명단·협상 상대·인물 카드가 같은 ID와
상태를 읽고, 각 도메인은 자기 판단에 필요한 파생값만 계산한다.

## 검증

핵심 회귀 검증은 금액 보존, 중복 방지, 권한과 경계, 상태 전이, 같은 입력의 같은 경기다.
모델 호출은 스키마와 mock으로 검사한다. 대화의 문구나 휴리스틱의 임의 문턱을
고정하는 테스트는 서비스 계약이 아니다. 국내 컵·유럽 대회·달력·훈련 일정의 시즌 검증은
간이 정산을 사용하며, 공식 경기 테스트의 프리시즌 준비도 같은 경로를 쓴다.
월간 회계는 고정 경기 결과와 실제 재정 정산 함수로 검증한다.
실시간 물리와 결산의 통합 검증은 실제 공간 시뮬레이터를 실행한다.
밸런스의 관측은 테스트와 별도 하네스다.

## 불변식

- 모델 출력은 Zod 검증과 코어 명령을 통과한다.
- 경기 입력·시드·명령의 재생은 서버 확정 원장을 기준으로 한다. 브라우저와 서버의
  동일 결과가 계약이다. 공통 능력치 곡선도 결정론적 수학 함수를 사용한다. 검증 지문은
  경기 설정·공간 상태·전술·시트·교체 대기·사건 원장을 포함한다.
- 원장이 소유하는 사실은 기억이나 화면이 다시 판정하지 않는다.
- 구조나 저장된 값의 의미가 바뀌면 저장 버전을 올린다. 이전 저장은 변환하지 않는다.

세부 규칙은 [문서 지도](README.md)를 따른다.

호출의 표시 이름은 `domain/src/common/call-labels.ts` 한 곳에 정의한다. 에이전트 카탈로그와
브라우저가 같은 순수 데이터를 읽으므로 UI에 서버 모듈을 끌어오거나 이름을 복사하지 않는다.

화면 조회도 책임에 따라 나눈다. 경기·대회는 `match/views`, 재정·협상·스카우팅은
`negotiation/views`가 만든다. 여러 경험의 정보를 엮는 선수단·경력·달력·선수 카드는
`app`의 조회이며, 별도 상태를 저장하지 않는다. 테스트 폴더도 같은 도메인 구분을 따른다.

## 의존성의 방향

공유 정보 `common`을 각 도메인이 사용하고, `app`이 도메인을 조립한다.
`story`, `negotiation`, `match` 사이에는 실행 의존성을 두지 않는다.
계약 타결 뒤 기자회견을 열거나 경기 뒤 재정을 정산하는 일은 `app`의 업무 흐름이다.
도메인은 자기 규칙과 상태 전이를 제공하며 다른 도메인의 결과를 직접 실행하지 않는다.
세 경험이 함께 읽는 선수 관측, 선수단 가용성, 인물 신원, 일정·순위 사실은 공통 조회다.
공통 조회는 상위 도메인 명령을 실행하지 않는다.

통합 화면도 같은 규칙을 따른다. 여러 도메인의 정보를 엮는 명단·경력 화면은 `app`이
조립하며, 도메인 화면에 다른 도메인의 기능이 필요하면 상위 화면이 콜백이나 콘텐츠로 제공한다.

`packages/engine/src/app/workflows`는 여러 도메인의 명령을 연결하는 게임 업무 흐름이다.
`packages/agents/src/app/workflows`는 모델·도구·상태를 연결하는 호출 흐름이다.
실행 함수가 이 계층에 있어도 프롬프트, 출력 스키마, 수치 규칙과 원장은 각 소유 도메인을 따른다.
웹의 채팅·입력줄·달력과 서버 요청 처리는 `application`에서 도메인별 화면을 조립한다.

ESLint는 도메인 간 값 import, 도메인에서 app으로 향하는 값 import,
공통 코드에서 상위 도메인으로 향하는 값 import를 금지한다. 패키지 내부에서 자기 공개
배럴을 다시 불러 경계를 우회할 수도 없다. 공개 패키지 API의 재노출도 실제 선언 위치를 따라 검사한다. 타입만 공유하는 참조는 허용하며 실행 의존성이
생기지 않는다. 브라우저에서 서버 엔진을 값으로 불러오는 것도 별도 규칙으로 막는다.

경기 입력 조립은 `match/squad/simulation.ts`, 대회가 공유하는 라운드로빈 대진은 `match/competition/pairings.ts`가 맡는다. 선수의 수상 조회와 은퇴 예고 철회는 `common/players/career.ts`에 있다. 이 함수들은 app의 시간 진행이나 시즌 전환을 호출하지 않는다.

도메인 모델의 공통 원장에는 선수의 출전·수상·성장·약속, 팀 전술 정보, 감독 계약·평판도 포함한다. 경험별 도메인은 이 공유 사실을 읽고 자기 명령으로 변경한다. 회견·협상 장면 모델과 출력 스키마는 해당 도메인에 둔다. 패키지 공개 API를 거치는 참조도 선언의 실제 소유 도메인을 기준으로 검사한다.

전술 지시의 검증과 실행은 호출자가 만든 동일한 명령 카탈로그를 사용한다. 적용 함수는 도구 팩터리를 다시 부르지 않는다. 경기 사건·팀 이름의 표시 조회는 `agents/src/match/context.ts`에 있고 GM 도구 조립을 참조하지 않는다.

## 서버 요청과 화면 갱신

쓰기 요청은 게임 잠금 안에서 상태를 읽고 검증한다. 응답에 필요한 파생 뷰와 추적
요약은 저장 전에 만든다. 저장이 성공한 명령만 재전송 방지 목록에 기록한다.
저장 이후의 전달 실패는 미저장 실패로 보고해 같은 명령을 재실행하지 않는다.
부분 화면 응답은 요청한 뷰만 계산한다. 전체 턴 응답은 모든 뷰를 갱신한다.

받아쓰기 도구는 명령 목록이 있다는 이유만으로 성공을 반환하지 않는다. 검증된
명령의 실제 성공·실패 수를 집계하고, 전부 반려되면 실패로 답한다. 인자 검증과
실행이 같은 카탈로그를 사용하며 킥오프 조회도 그 카탈로그를 재사용한다.

경기 통신에 실패하면 로컬 진행도 멈춘다. 사용자가 재개하면 서버 확정 상태부터
다시 잇는다. 취소된 드래그는 전술 변경이 아니며, 화면을 떠나면 포인터 구독을 해제한다.

전체 응답의 선수 이름 색인은 선수 ID·이름이 같을 때 재사용하며, 같은 대화 본문의
선수 언급도 제한된 메모리 캐시에서 읽는다. 경기 이름 사전에는 벤치를 포함한 양 팀
명단이 들어가므로 교체된 선수의 과거 사건도 이름으로 남는다.

경기·협상 카드의 스타일은 각 도메인의 CSS에 있다. 공통 코드는 대화창의 배치,
접근성 포커스 처리, 복사 동작처럼 여러 경험에서 쓰는 동작만 제공한다.
