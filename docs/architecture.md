# story-fm의 책임 구조

story-fm은 자연어로 감독이 되어 살아가는 게임이다. 재미의 중심은 스토리·협상·경기다.

1. **구단의 일상과 서사** — 메인 GM이 훈련·면담·기자회견을 진행한다. 인물의 기억과 관계, 감독의 선택이 다음 장면에 이어진다.
2. **협상** — 메인 대화에서 만나거나 통화하고 메일함에서 조건과 자료를 주고받는다. 메인 GM이 참여자를 연기하고 코어가 협상 조건과 집행을 검증한다.
3. **실시간 경기** — 선수와 전술이 공간 시뮬레이터에서 경쟁한다. 감독은 자유롭게 개입하고, 검증된 지시가 다음 구간의 플레이를 바꾼다.

세 경험은 플레이어가 겪는 갈래다. 코드와 문서는 이 갈래가 아니라 축구의 다섯 낱말 — 선수·
경기·시즌·팀·인물 — 로 나뉜다. 선수·계약·재정·대회는 세 경험이 모두 읽기 때문이다 (§1).

## 책임의 경계

AI는 의미를 해석하고 인물의 반응과 이야기를 판단한다. 코어는 대상의 존재, 소유권,
날짜, 계약, 지출 가능 여부, 수치의 범위와 누계를 검증한다. 자유 텍스트로 장부를
바꾸지 않으며, 검증을 통과한 구조적 출력만 결정적 명령으로 반영한다.

선수 능력치·포지션·역할·체력·적응도·폼은 감독이 판단할 수 있는 정보다.
경기 결과와 재정의 사실은 모델이 서술한 결과가 아니라 시뮬레이션과 원장이 정한다.
대표팀 소집과 세계 유스 생성은 배경 축구 시뮬레이션으로 진행한다. 날짜·시즌의 흐름(`app`)이
이 규칙들을 호출하며 일반 대화의 감정·관계 판단과 구분한다.

## 1. 도메인

| 도메인    | 소유하는 일                                                                 | 문서                         |
| --------- | --------------------------------------------------------------------------- | ---------------------------- |
| `players` | 선수 — 선수 카탈로그·능력·부상·폼·관측·전술 적응도·훈련·성장·유스·은퇴·경력 | [players](players/README.md) |
| `match`   | 경기 시뮬레이션 — 입력 조립·경기 흐름·간이 시뮬·평점·징계·연장·승부차기     | [match](match/README.md)     |
| `season`  | 시즌 — 일정·편성·리그·국내 컵·유럽 대항전·대표팀·순위·상금·시상·구단 역사   | [season](season/README.md)   |
| `team`    | 팀 — 선수단·등록·라인업·전술·이적·계약·재정·이사회 요청·구단 정체성         | [team](team/README.md)       |
| `people`  | 인물 — 인물 카탈로그·로어북·스태프·메일함·언론·감독의 고용과 커리어         | [people](people/README.md)   |

도메인이 아닌 것이 둘 있다.

- **`core`** — 모든 도메인이 딛는 바닥. 게임 상태(`GameState`)와 그 위의 조회·기록 원시 연산
  (날짜·난수·이름 해석·장부 기록·저널·저장 잠금), 그리고 게임 상태가 직접 읽는 세계의 기준 표
  (팀·리그·컵·징계 카탈로그). 규칙과 밸런스 수치는 갖지 않는다 ([core](core/README.md)).
- **`app`** — 여러 도메인을 함께 움직이는 일. 새 게임·하루와 시즌의 진행·저장·GM 조회·통합
  화면·도메인을 가로지르는 업무 흐름·어드민 ([app](app/README.md)).

호출의 갈래(`config/llm.yml`의 에이전트)는 [agents](agents/README.md), 화면은
[web](web/README.md)이 소유한다.

## 2. 의존 방향

엔진은 아래에서 위로 쌓인다. 한 도메인은 **자기보다 아래**만 값으로 부른다.

```
core → players → match → season → team → people → app
```

- `players`는 선수 한 사람의 상태만 안다. 전술 적응도도 "그 선수가 그 판에 얼마나 익었나"라
  선수의 상태이고, 훈련 결산이 그것을 올린다.
- `match`는 선수를 읽어 경기를 굴린다. 감독이 짜는 판(라인업·전술)은 `team`의 것이고,
  `match`는 시뮬레이터에 넣을 명단을 고르는 규칙(`selection`)만 갖는다 — `team`이 그 규칙을 부른다.
- `season`은 경기들을 대회로 엮는다. 상금은 `core`의 장부 연산으로만 기록하고, 재정 모델은 모른다.
- `team`의 재정 모델은 순위와 경기 결과(`season`)를 읽어 돈을 움직인다. 이적은 선수·경기·시즌의
  사실을 모두 읽는다.
- `people`이 맨 위다 — 인물은 아래의 모든 사실을 읽어 말과 기사·메일로 옮긴다. 감독과 스태프의
  고용은 구단 재정(`team`)을 읽는다.

**여러 도메인을 함께 움직이는 흐름은 `app/workflows`에 둔다** — 경기 뒤 결산(`match-flow`),
훈련 결산의 반영과 보고 메일(`training-report`), 승강과 낙하산(`promotion`), 이사회의 경질·선임
(`board`·`manager-employment`), 날짜 진행 중 세계 시장(`world-market`), 로어북 등록과 주입의
원장 사실(`lorebook`). 실행 함수가 `app`에 있어도 수치 규칙과 원장은 소유 도메인에 있다.

두 도메인이 같은 규칙을 필요로 하면 규칙이 **아래로** 내려간다 — 순수 데이터 규칙은
`packages/domain`, 결정성 원시 연산은 `packages/sim`, 엔진 안의 규칙은 둘이 공통으로 딛는
도메인이나 `core`로. 타입만 공유하는 참조는 방향과 무관하다.

ESLint가 이 방향을 강제한다(`eslint.config.js`의 `engineLayers`). 패키지 내부에서 자기 공개
배럴을 다시 불러 경계를 우회할 수도 없다.

## 3. 패키지

| 패키지            | 폴더의 축                                                                    | 경계                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `packages/domain` | 도메인 + `core` — 브라우저에서 안전한 Zod 모델과 순수 규칙                   | 모든 도메인이 읽는 **공용 어휘**라 폴더끼리 서로 읽는다. `app/`(화면 조작의 모양)만은 모델이 읽지 않는다 |
| `packages/engine` | 도메인 + `core` + `app` — 결정적 명령과 조회                                 | §2의 층                                                                                                  |
| `packages/agents` | 호출의 갈래 — Jev 평가(`evaluators`) · 기억(`memory`) · 장면을 쓰는 GM(`gm`) | `shared` → `evaluators`·`memory` → `gm` → `app`                                                          |
| `packages/sim`    | 경기 전용 결정적 공간 코어                                                   | `node:`를 import하지 않는다                                                                              |
| `packages/llm`    | 제공자 어댑터와 추적                                                         |                                                                                                          |
| `apps/web`        | 화면 — `game/`(껍데기와 서버 배관) · `screens/<화면>` · `shared/` · `dev/`   | 화면은 `shared/`만 부르고 서로를 부르지 않는다. 화면을 엮는 일은 `game/`이 한다                          |

에이전트 폴더는 `config/llm.yml`의 갈래를 따른다. `evaluators`는 Jev 평가 호출 전부 —
지시 해석기와 tactic·training·finance 지시 평가, 경기 판독(`match-reader`), 경기 마감
(`finalize-match`), 훈련 결산(`training-rater`)이다. `memory`는 로어북 편집과 이력 압축,
`gm`은 장면을 쓰는 호출 — 평시 GM·경기 GM·첫 장면 검사·메일 회신 — 이다. 경기 GM은 평시 GM의
도구 바인딩에서 경기 도구를 고르므로 둘이 한 폴더에 있다. 턴을 라우팅하고 시간 진행·mock·
온보딩을 엮는 일은 `app`이다.

테스트 폴더(`packages/*/test/`, `apps/web/test/`)는 같은 축을 따른다. 패키지 공개 API는
각 `index.ts`가 재노출하며, 패키지 안에서는 소유 모듈을 직접 import한다.

## 기억과 이야기

[로어북과 대화 요약](people/lorebook.md)이 서사를 보존한다. 로어북은 팀·선수·
인물의 자유 기록이고, 요약은 지난 대화와 열린 이야기 및 인물 후보 목록이다.
메인·경기 GM과 세계 업무 처리가 편집 스킬을 호출하면 별도 에이전트가 로어북을 비동기로 갱신한다.
요약 에이전트는 로어북을 편집하지 않는다. 키워드로 주입한 항목은 해당 턴의
본문을 보존하며, 현재 이력 안의 같은 버전은 중복 주입하지 않는다.
관계·감정·불만·시작 사건·회견·일반 면담의 상태와 자동 수치 반응은 두지 않는다.
코어는 경기·몸 상태·계약·재정·고용의 사실과 권한을 검증한다.

## 계약과 장부

선수 계약은 초기·유스 계약과 협상으로 체결한 소속·주급·기간을 기록한다. 모든 구단은 계약 만료 시
선수를 무소속으로 전환한다. 선수 영입·매각·재계약은 [협상](team/transfers.md)의 검증된 명령으로 실행한다.
[재정](team/finance.md)은 수입·지출·자산 상각과 월간 보고서를 소유한다.
감독·스태프의 고용은 GM이 합의된 조건을 기록하고 코어가 재직·권한·지출을 검증한다.

## 상태와 세계 생성

`packages/engine/src/core/state.ts`는 상태의 형태, 조회와 작은 장부 연산을 소유한다. 세계 생성·일정
편성·경기 진행·선수단 선택을 import하지 않는다. 대표팀 소집과 부상·징계에 따른
현재 가용성도 저장된 사실을 읽는 조회이며, 대표팀 시뮬레이션을 호출하지 않는다.

새 게임 생성은 `packages/engine/src/app/create-game.ts`가 카탈로그·선수 생성·대회·훈련·인물 초기화를
조립한다. 포메이션 평가와 선발·벤치 선택은 `packages/engine/src/match/selection.ts`의 한 규칙을
초기 편성과 시즌 중 재편성이 함께 사용한다. 경기 입력 조립은 `packages/engine/src/match/simulation.ts`,
대회가 공유하는 라운드로빈 대진은 `packages/engine/src/season/pairings.ts`가 맡는다.

## 보드와 고용

구단주와 감독의 기대와 평가·신뢰는 로어북과 대화에 남는다. 유저의 고용·재계약은
GM이 판단하고 코어가 계약과 정산을 검증한다. 다른 구단의 경질·선임은 날짜 진행 시
코어가 실제 성적·재임 기간·부상·감독 후보를 기준으로 결정한다. `review_board`는
실제 경질·AI 감독 선임을, `offer_manager_job`은 명시적인 계약 제안을 기록한다.
유저의 부임·재계약에는 수락이 필요하다.

## 조회와 화면

GM이 부르는 조회 도구는 `packages/engine/src/app/lookup/`에 도구 하나가 파일 하나로 있다.
화면 뷰는 소유 도메인이 만든다 — 경기 중계는 `match/live-view.ts`, 대회는
`season/competition-view.ts`, 재정은 `team/finance-view.ts`. 여러 도메인을 엮는
선수단·경력·달력·선수 카드·경기 리포트는 `app/views/`의 조회이며 별도 상태를 저장하지 않는다.

호출의 표시 이름은 `packages/domain/src/app/call-labels.ts` 한 곳에 정의한다. 에이전트 카탈로그와
브라우저가 같은 순수 데이터를 읽으므로 화면에 서버 모듈을 끌어오거나 이름을 복사하지 않는다.
화면은 엔진을 타입으로만 가져온다. 서버에서만 도는 `apps/web/game/` 모듈(`store`·`turn-runner`·
`lorebook-jobs`·`live-match-server`)도 화면이 값으로 부르지 않는다.

전술 지시의 검증과 실행은 호출자가 만든 동일한 명령 카탈로그를 사용한다. 적용 함수는 도구
팩터리를 다시 부르지 않는다. 경기 사건·팀 이름의 표시 조회는
`packages/agents/src/shared/match-context.ts`에 있고 GM 도구 조립을 참조하지 않는다.

## 서버 요청과 화면 갱신

쓰기 요청은 게임 잠금 안에서 상태를 읽고 검증한다. 응답에 필요한 파생 뷰와 추적
요약은 저장 전에 만든다. 저장이 성공한 명령만 재전송 방지 목록에 기록한다.
저장 이후의 전달 실패는 미저장 실패로 보고해 같은 명령을 재실행하지 않는다.
부분 화면 응답은 요청한 뷰만 계산한다. 전체 턴 응답은 모든 뷰를 갱신한다.

받아쓰기 도구는 명령 목록이 있다는 이유만으로 성공을 반환하지 않는다. 검증된
명령의 실제 성공·실패 수를 집계하고, 전부 반려되면 실패로 답한다. 인자 검증과
실행이 같은 카탈로그를 사용하며 킥오프 조회도 그 카탈로그를 재사용한다.

경기 통신에 실패하면 로컬 진행도 멈춘다. 사용자가 재개하면 서버 확정 상태부터
다시 잇는다. 취소된 드래그는 전술 변경이 아니며, 화면을 떠나면 포인터 구독을 해제한다.

전체 응답의 선수 이름 색인은 선수 ID·이름이 같을 때 재사용하며, 같은 대화 본문의
선수 언급도 제한된 메모리 캐시에서 읽는다. 경기 이름 사전에는 벤치를 포함한 양 팀
명단이 들어가므로 교체된 선수의 과거 사건도 이름으로 남는다.

경기 카드의 스타일은 그 화면의 CSS에 있다. `shared/`는 여러 화면이 쓰는 조각, 접근성
포커스 처리, 복사 동작처럼 공통 동작만 제공한다.

NPC 구단의 시장 판단과 거래는 결정적 엔진(`team`)에서 실행한다. 메인 GM이 만남·통화·메일로
협상하고, 메일 회신은 게임 날짜에 도래한 업무로 실행한다. 메일·협상 원장의 연결과 감독의
확인 조작은 `app`과 `game/`이 조립한다.

## 검증

핵심 회귀 검증은 금액 보존, 중복 방지, 권한과 경계, 상태 전이, 같은 입력의 같은 경기다.
모델 호출은 스키마와 mock으로 검사한다. 대화의 문구나 휴리스틱의 임의 문턱을
고정하는 테스트는 서비스 계약이 아니다. 국내 컵·유럽 대회·달력·훈련 일정의 시즌 검증은
간이 정산을 사용하며, 공식 경기 테스트의 프리시즌 준비도 같은 경로를 쓴다.
월간 회계는 고정 경기 결과와 실제 재정 정산 함수로 검증한다.
실시간 물리와 결산의 통합 검증은 실제 공간 시뮬레이터를 실행한다.
밸런스의 관측은 테스트와 별도 [하네스](balance-harness.md)다.

## 불변식

- 모델 출력은 Zod 검증과 코어 명령을 통과한다.
- 경기 입력·시드·명령의 재생은 서버 확정 원장을 기준으로 한다. 브라우저와 서버의
  동일 결과가 계약이다. 공통 능력치 곡선도 결정론적 수학 함수를 사용한다. 검증 지문은
  경기 설정·공간 상태·전술·시트·교체 대기·사건 원장을 포함한다.
- 원장이 소유하는 사실은 기억이나 화면이 다시 판정하지 않는다.
- 구조나 저장된 값의 의미가 바뀌면 저장 버전을 올린다. 이전 저장은 변환하지 않는다.

세부 규칙은 [문서 지도](README.md)를 따른다.
